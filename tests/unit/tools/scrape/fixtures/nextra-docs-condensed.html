Setup locale-based routing

In order to use unique pathnames for every language that your app supports, next-intl can be used to handle the following routing setups, and the choice between them depends on how your deployment is organised, how your marketing team wants the URLs to read, and whether you already own the country-level domains involved.

  1. Prefix-based routing (e.g. /en/about)
  2. Domain-based routing (e.g. en.example.com/about)

In either case, next-intl integrates with the App Router by using a top-level dynamic segment that can be used to provide content in different languages, and the remainder of this page walks through the four files involved, in the order you will want to create them, with the configuration for each one explained as it appears.

Initial setup

To get started with locale-based routing, we will set up the following files, beginning with a central routing configuration that every other file reads from, so that the list of supported locales and the default locale are declared exactly once and stay consistent across the proxy, the navigation helpers and the request configuration.

import {defineRouting} from 'next-intl/routing';

export const routing = defineRouting({
  locales: ['en', 'de'],
  defaultLocale: 'en'
});

Depending on your requirements, you may wish to customize your routing configuration later, adding domain definitions or per-locale pathnames, but it is easier to finish the setup with the defaults in place first and confirm that a request actually reaches the right page before layering anything else on top of it.

import createMiddleware from 'next-intl/middleware';
export default createMiddleware(routing);

Static rendering

⚠️
setRequestLocale is a legacy API that was added until next/root-params was introduced. It is still supported for backwards compatibility, but it is recommended to use next/root-params instead.

When using locale-based routing, next-intl will currently opt into dynamic rendering when APIs like useTranslations are used in Server Components. This is a limitation that we aim to remove in the future, but as a stopgap solution there is a temporary API that can be used to enable static rendering for the routes that need it.

import {setRequestLocale} from 'next-intl/server';

export default async function LocaleLayout({children, params}) {
  const {locale} = await params;
  // Enable static rendering
  setRequestLocale(locale);
}

Keep in mind that the locale you pass to it should be validated in your root layout, that you need to call this function in every page and every layout that you intend to enable static rendering for, and that it has to run before you invoke any other function from the library or the request-scoped store will not have been populated yet.
